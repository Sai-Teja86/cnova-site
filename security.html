Security architecture

How Vaultgate protects the keys to everything

A privileged access platform holds your most sensitive secrets, so it is built to be hard to break into and easy to check.

Protecting credentials

🔑

Envelope encryption

Each credential is sealed with AES-256-GCM under its own data key. Data keys are wrapped by a master key that each appliance generates on first start. A copy of the database alone reveals nothing.

🧷

Bound to its record

Every ciphertext is bound to the record it belongs to, so a secret moved onto another account fails to decrypt.

🙈

Credential injection

In brokered sessions the password goes from the vault to the server through the gateway. It never reaches the user's browser or computer.

🛡️

Control accounts kept apart

Administrator logins used for rotation are visible to administrators only, never offered to users, and never handed out through the API.

Protecting sessions

Pinned host keys

A server's SSH key is pinned on first use. If it changes, connections stop and the event is logged until an administrator checks it, which blocks interception.

Certificate checks

RDP certificates are validated by default. The RemoteApp launcher talks to Vaultgate over HTTPS pinned to the appliance's certificate.

Single-use tickets

Browser sessions open with short-lived, single-use tickets, and the policy is checked again at the moment of connection.

Read-only monitoring

People watching a live session can't type or click into it: their keyboard and mouse input is dropped.

Protecting the evidence

Chained audit trail

Every event is linked to the one before it with HMAC-SHA256. Editing or deleting an entry breaks the chain, and the check is one click. Export it as CSV for your SIEM or archive as well.

Sealed recordings

Each recording's SHA-256 is written into the audit trail when the session ends, and checked every time it is replayed.

File contents kept out

Transferred files are logged by name, size and hash, and their contents are kept out of the recordings.

Never run blind

If the disk is close to full, new sessions are refused rather than run without a recording.

Protecting the appliance

Sign-inArgon2id password hashing, TOTP multi-factor (on by default for the first administrator, and can be required for everyone), lockout after failed attempts, token revocation
Single sign-onOpenID Connect with PKCE; the ID token's signature, issuer, audience, expiry and nonce are all checked
DirectoryLDAPS or StartTLS with certificate checks; empty passwords refused
NetworkFirewall open only on 443 (web) and 2200 (SSH gateway); the remote-desktop engine listens on loopback only
Web consoleStrict Content-Security-Policy with no inline script, framing denied, no caching of API responses
Operating systemDebian 12 with a firewall that drops all other traffic; root is locked and the server screen shows a console, not a login prompt
Unique secretsEvery installation makes its own master key, TLS certificate, SSH host key and database; nothing secret ships on the installer
UpdatesEd25519-signed bundles, checked before anything is installed
BackupsAES-256-GCM, with the key derived from your passphrase; the passphrase is never stored
