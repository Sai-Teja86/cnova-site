Vault

Credential vault and checkout

One encrypted home for every privileged password and key.

  • AES-256-GCM envelope encryption: a separate key for every secret, wrapped by the appliance's master key
  • Each secret is bound to its own record, so it can't be copied onto another account
  • Every password version is kept, with who changed it and when
  • Checkout with a reason and a time limit, and an exclusive lock so two people don't use one account
  • Automatic check-in when the time runs out, with optional rotation on check-in
  • Linked accounts: one domain account used on many servers, rotated once for all of them
  • Control accounts: the administrator logins used for rotation are kept apart from users and seen by administrators only
  • SSH keys as well as passwords
How it works

When a password or key is saved, Vaultgate makes a new random 256-bit data key for it, encrypts the secret with AES-256-GCM, and stores the data key only in wrapped form, encrypted by the appliance's master key. The record's identity is part of the encryption, so a ciphertext copied onto another account won't open.

  1. Checkout. A user with the reveal right gives a reason and a duration. The account is locked to them, so nobody else can check it out meanwhile, and the reveal is audited.
  2. Check-in. The user returns it, or the time runs out and Vaultgate returns it. If the account's rotation policy says so, the password changes straight away, so what the user saw no longer works.
  3. History. Each change adds a version, encrypted the same way, with who made it and why: a scheduled rotation, a check-in, or an edit.

Linked accounts let one domain account serve many servers: it's stored and rotated once, and each server it's linked to offers it for sessions. Control accounts are the administrator logins Vaultgate uses for rotation and account creation. They're seen by administrators only, never granted to users, and their own rotation is off until an administrator allows it.

Rotation

Automatic password rotation

Passwords change by themselves and are checked every time.

  • Named rotation policies: schedule, length, symbols and characters to avoid
  • Rotate after each use, for one-time passwords
  • Changed by the account itself, or by a control account for accounts whose password nobody knows
  • Each new password is checked with a real sign-in, and failures are flagged
  • Linux and Unix, Windows local and domain accounts, 9 database engines, Cisco IOS and FortiGate
  • Custom platforms: write the commands for any SSH device as send and expect steps
  • On-demand rotation, and failures shown with the reason
  • Full list of supported systems →
How it works
  1. Due. Every minute the scheduler looks for accounts whose rotation policy is due: a number of days since the last change, or a use that just ended.
  2. New password. It's generated to the policy: 12 to 128 characters, symbols or not, and without characters the target can't take.
  3. Change. Vaultgate signs in to the target and changes it: as the account itself, or through a control account for accounts whose password nobody knows. Each platform uses its own command, such as passwd, ALTER LOGIN or an LDAPS password modify.
  4. Store. The new password becomes the current version. The previous one stays in the history.
  5. Check. Vaultgate signs in with the new password. If that works the rotation is marked successful; if not, it's marked unverified with the reason, for an administrator to look at.

Lockout safety: if the target refuses the password Vaultgate holds, automatic rotation of that account stops rather than retrying, so it can't lock the account out. It resumes once the password is corrected or a test login passes. During a failover, a primary that has lost contact with both its standby and witness also holds rotations, so two appliances can never set different passwords.

Remote access

Brokered sessions

Users connect without ever receiving the password.

  • SSH in the browser, with the password or key injected by the gateway
  • RDP and VNC desktops in the browser, with nothing to install
  • Native SSH gateway: ssh, scp, sftp and rsync work unchanged
  • Pick a target from a menu, or go straight to it: ssh alice+root@web-01@vaultgate
  • Target host keys pinned on first use; a changed key blocks the connection
  • RDP certificate validation on by default
  • Maximum session length and automatic end of idle sessions
  • Each session opens in its own browser tab
How it works
  1. Choose. The user picks an account and server from My access. The policy is checked: rights, time window, approval.
  2. Ticket. The browser receives a single-use ticket valid for 30 seconds. It carries no password.
  3. Connect. The gateway checks the policy again, then opens the connection to the server itself: SSH with the host key pinned at first use, or RDP and VNC through the appliance's own remote desktop engine, with the RDP certificate validated.
  4. Sign in. The gateway types the password or presents the key. The user sees the server, never the credential.
  5. During. Everything passes through the gateway, which applies the policy's controls, records the session and lets administrators watch or end it.
  6. End. At logout, after 15 minutes idle, at the policy's maximum length, or when access is withdrawn. If the policy rotates after use, the password changes next.

Native SSH: people who prefer their own terminal connect to the gateway on port 2200 with their Vaultgate login: ssh alice@vaultgate shows a menu of what they may reach, and ssh alice+root@web-01@vaultgate goes straight there. scp, sftp and rsync work the same way, under the same policy and recording.

Session control

What users can and can't do

Stop risky actions before they reach the server.

  • Command blocklists per policy, checked before the command reaches the server
  • Works for Linux shells and for Windows cmd and PowerShell over SSH, with each chained Windows command checked on its own
  • Keyword guard for RDP, VNC and applications: blocked words typed in a graphical session are stopped
  • Clipboard allowed or blocked per policy
  • File upload and download as separate permissions, off by default
  • Blocked file types, checked by their real contents, and blocked words inside text, Office and zip files
  • Each transferred file's name, size and SHA-256 logged
  • Printing disabled in remote desktops
How it works

Controls are set per policy. When several policies apply to a session, their blocked commands and words add up.

  • Commands (SSH). The gateway rebuilds each line as it's typed and, when Enter is pressed, matches it against the policy's patterns. A blocked line is cancelled instead of sent, the user sees why, and the attempt is audited. On Windows servers every command in a chained line is checked on its own, program paths are reduced to the program name, and cmd /c and powershell -Command wrappers are unwrapped. Like any typed-line filter it complements least-privilege accounts rather than replacing them, which is what personal JIT accounts give you.
  • Keyword guard (RDP, VNC, applications). Typed text is checked as it's entered. The policy chooses whether a match warns the user or ends the session; either way it's audited.
  • Files (RDP). Uploads and downloads are separate rights. Each file is checked on the way: its type is read from its contents, not its name, and text, Office and zip files are searched for blocked words. Allowed transfers are logged with name, size and SHA-256.
  • Files (SSH). SCP and SFTP through the gateway need their own right in the policy.
  • Clipboard and printing. The clipboard is allowed or blocked per policy. Printing from remote desktops is off.
Evidence

Recording, monitoring and audit

See everything, change nothing unnoticed.

  • SSH, RDP and VNC sessions recorded and replayed in the browser, with seeking (how recordings are handled)
  • Each recording's SHA-256 sealed into the audit trail and checked on replay
  • Commands and typed lines indexed and searchable across all recordings
  • Watch live sessions read-only; end any session at once
  • HMAC-chained audit trail of every sign-in, decision, reveal, session and change, with one-click integrity check
  • Audit views by category: sign-ins, sessions, credentials, access, identity, configuration
  • CSV export of every view, and a PDF management report with charts and findings
  • Every audit event forwarded to your SIEM as it happens, over syslog with TLS, and nothing lost while it's down
  • Recording compression, retention periods of 180 days or more, and disk-space alerts; sessions refused before the disk fills
How it works
  • Recording. SSH sessions are recorded as text, so a replay is sharp at any size and every command can be searched. Remote desktop sessions are recorded as the screen stream. Both replay in the browser with a timeline.
  • Sealing. When a session ends, its recording's SHA-256 is written into the audit trail. A replay recomputes it, and a mismatch is shown.
  • Searching. Commands and typed lines are indexed per session, so an auditor can find every session where someone ran a given command and jump to that moment.
  • The audit chain. Every event carries an HMAC-SHA256 over its own content and the previous event's. Changing, deleting or reordering any entry breaks the chain from that point, and the integrity check shows the first broken entry.
  • Reporting. Each audit view exports to CSV for your archive. The management report summarises access, sessions, rotations and findings as a PDF.
  • SIEM forwarding. Each event goes to your syslog collector or SIEM as it's written: RFC 5424 syslog with a JSON body, over TLS, TCP or UDP. Every message carries the event's chain hash, so your SOC's copy can be checked against the appliance. Vaultgate remembers the last event the collector took; while it's unreachable events wait, and they're sent in order once it's back.
  • Time you can rely on. Timestamps are only evidence if the clock is right. Set the NTP servers from the console (NIC and NPL in one click), see the offset and the servers in use, and get an alert if the clock loses sync.
Recordings

How recordings are handled

A session recording is evidence, and it can show code, data and anything typed on screen. Vaultgate treats it that way from the moment it's made until it's deleted: you decide what's recorded, who sees it, and whether it may ever leave the appliance.

  1. Recorded where it mattersEvery SSH, RDP, VNC and application session is recorded by default. Switch recording off per server, for example on test and UAT systems, and those sessions use no recording space while staying brokered, audited, command-indexed and watchable live.
  2. Sealed when the session endsEach recording's SHA-256 goes into the tamper-evident audit trail. Every replay checks it, so a changed recording shows up at once.
  3. Kept to what's neededPasswords Vaultgate types in are never in a recording, and transferred files' contents are kept out of it. Keystroke logs are encrypted with the vault key. Recordings are compressed, kept for the period you set, and disk alerts warn before space runs out.
  4. Watched only by the right peopleOnly administrators and auditors can replay or monitor sessions, and every replay is in the audit log, with who watched what, and when.
  5. Leaves only if you allow itDownloads are one setting, changed only with an administrator's password and MFA code: off, plain evidence package, or encrypted.
  6. Encrypted files stay yoursAn encrypted download needs a passphrase shown once and a key that never leaves the appliance. It opens only on the appliance that made it, under Sessions, with each opening audited. A copied file and its passphrase are useless anywhere else.

Built for compliance

Turn downloads off and recordings never leave the appliance: they can only be replayed in the console, by the people allowed to, on the record.

Survives failover and restore

The standby can take a daily copy of recordings, and encrypted downloads still open after a failover or on an appliance restored from your backup.

Space where it counts

Record production and sensitive systems in full, skip the test and UAT servers people use all day, and let retention clear out the rest.

Least privilege

Access policies and just-in-time access

Nobody gets anything until a policy says so.

  • Deny by default
  • Grant to a user, role or directory group, for an account, a server, a tag or everything
  • Separate rights to open a session and to see a password
  • Day and hour windows, and a maximum session length
  • Access requests with a reason and duration, approved or refused by an approver
  • No self-approval; access ends on time, and revoking it ends live sessions
  • Personal JIT accounts: each user or vendor gets their own account on Linux and Windows servers, in Active Directory (allowed only on the covered servers) or on a database, created when they connect and removed when access ends
  • Roles: administrator, approver, auditor and user
How it works

A policy says who (a user, role, directory group or Vaultgate group) may do what (open sessions, see passwords, or both) on which targets (one account, a server, a tag, or everything) and when (days, hours, maximum session length). With no matching policy, the answer is no.

  1. Direct access. If a matching policy needs no approval, the user connects.
  2. Approval. If approval is needed, the user asks with a reason and a duration. An approver decides; nobody can approve their own request. Access opens for the approved time only.
  3. Withdrawal. Revoking a grant ends the sessions that depend on it at once.

Personal JIT accounts: instead of sharing one account, a policy can give each person their own. At the first connection Vaultgate creates the account on the server, in Active Directory or on the database, with the groups or roles the policy names and a random password it keeps to itself. The person works under their own name, so the server's own logs show who did what. Ten minutes after their last session ends, or as soon as access is withdrawn, the account is removed; a removal that fails is retried every five minutes and shown to administrators until it succeeds.

Identity

Sign-in and directories

Use the accounts your people already have.

  • Any number of Active Directory and LDAP domains, with guided setup
  • OpenID Connect single sign-on
  • Users created on first sign-in, with their role taken from directory groups each time
  • Directory groups usable directly in policies
  • Regular sync: leavers disabled, group changes followed, sessions that are no longer allowed ended
  • TOTP multi-factor sign-in, which can be required for everyone
  • Argon2id password hashing, lockout after failed attempts, forced change on first sign-in
How it works
  1. Connect a directory. Add an Active Directory or LDAP domain with a guided form, over LDAPS or StartTLS with the certificate checked. Add as many as you have.
  2. Map roles. Choose which directory groups make someone an administrator, approver, auditor or user.
  3. Sign in. A directory user who signs in for the first time gets a Vaultgate user automatically, with the role taken from their groups, again at every sign-in.
  4. Stay in step. Every 15 minutes Vaultgate re-reads each directory: people who left are disabled and lose their live sessions, and group changes take effect.

Single sign-on works with any OpenID Connect provider, using the authorization code flow with PKCE, and checks the ID token's signature, issuer, audience, expiry and nonce. TOTP multi-factor can be required for everyone, and sensitive settings ask again for the administrator's password and code.

Onboarding

Discovery and bulk import

Bring hundreds of servers and accounts in at once.

  • Find computers in Active Directory, or scan address ranges, and add them as RDP or SSH servers
  • Find privileged and service accounts by group, OU, name or admin flag
  • Discover local accounts on Windows servers
  • CSV import of servers and accounts with a full preview; nothing is saved while any row has an error
  • New accounts get a fresh password straight away, so nobody needs to know the current one
  • Connection test page: port reachability and sign-in for every account, in one click
How it works
  1. Discover. Search Active Directory for computers, by OU or operating system, and for privileged and service accounts, by group (nested groups included), OU, name or admin flag. Scan address ranges for SSH, RDP and VNC servers. Read local accounts from Windows servers.
  2. Or import. Upload a CSV of servers and accounts. Every row is checked and shown in a preview first; nothing is saved while any row has an error.
  3. Take over. New accounts can be given a fresh password at once, so the current one, whoever knows it, stops working.
  4. Test. The connection test page checks every server's port and every account's sign-in in one go, and lists what needs fixing.
Automation

Credential API

For scanners, pipelines and scripts.

  • Applications fetch a password over HTTPS when they need it, so rotation never breaks them
  • Each application has its own API key (only a hash is stored) and optional expiry
  • Allowed source addresses, and the exact accounts or tags each application may fetch
  • Optional mandatory reason and rate limit
  • Every fetch and refusal audited; repeated failures block the address
  • Control accounts are never handed out through the API
How it works
  1. Register. An administrator adds the application, lists the addresses it calls from and the accounts or tags it may fetch, and gets an API key, shown once. Vaultgate keeps only its hash.
  2. Fetch. The application calls GET /api/v1/credential over HTTPS with the key, naming the account by id, name, address or user name, at the moment it needs the password.
  3. Checks. Source address, key, expiry, grant and rate limit are checked on every call. A mandatory reason can be required.
  4. Record. Each fetch and each refusal is audited. Ten failures from one address in five minutes block it for the rest of that window.

Because applications fetch the current password every time, rotation never breaks them. Control accounts and personal JIT accounts are never released through the API.

Applications

Application access (RemoteApp)

Give access to a program, not a whole desktop.

  • Published programs on a Windows RDS server open as one window in the browser
  • Examples: SQL Server Management Studio, AD Users and Computers, MMC consoles, browsers
  • A second vaulted login, such as a database account, can be passed into the program
  • One-time launch tokens and certificate-pinned HTTPS to the RDS server
  • Recorded and monitored like any remote desktop session
How it works
  1. Publish. On a Windows RDS server, publish the program as a RemoteApp, and install the small Vaultgate launcher if the program needs a second login.
  2. Describe. In Vaultgate, name the application, its RDS host account and, optionally, the vaulted account to put into it, such as a SQL Server login, and how: on the command line, typed into the sign-in window, or run as that account.
  3. Launch. The user clicks it. Vaultgate opens a RemoteApp session to the RDS host and passes a one-time token. The launcher redeems the token over HTTPS pinned to Vaultgate's certificate, receives the credential and starts the program with it.
  4. Watch. The session is recorded and monitored like any remote desktop, with the keyword guard and file controls of its policy.
Operations

Availability, backup and updates

Built to run unattended.

  • Automatic failover: primary, warm standby and a witness, with a virtual address that moves in about 45 seconds
  • Encrypted backups (AES-256-GCM, passphrase-protected), with or without recordings
  • Restore onto a new appliance from the setup wizard
  • Signed update bundles, checked before install; a failed update rolls back by itself
  • Updating a pair updates the standby and witness first
  • Recovery kit: emergency accounts in an encrypted file that opens offline, unlocked by a set number of recovery codes (for example 2 of 3)
  • Appliance console for network, time, license, storage and updates
  • Network tools in the console: ping, traceroute, port check and DNS lookup from the appliance, for troubleshooting connections
  • Email notifications through your mail server: access requests to approvers, decisions to requesters, and alerts to your team
How it works
  • Failover. The primary renews a lease from the witness every few seconds and answers on the virtual address. If the standby hears nothing for 30 seconds and the lease has run out, it takes the lease, restores the latest copy and takes over the address, about 45 seconds in all. The old primary is marked replaced and won't serve again until it rejoins.
  • Standby copy. After each change the primary sends an encrypted backup to the standby. Recordings follow once a day. The pairing secret never crosses the network.
  • Backups. Encrypted with a passphrase you choose, with or without recordings, and restorable on a new appliance from the setup wizard.
  • Updates. A signed bundle is uploaded and checked before anything changes. If the new version fails to start, the appliance rolls back by itself. In a pair, the standby and witness are updated first.
  • Email notifications. Vaultgate sends email through your own mail server over STARTTLS or TLS, with its certificate checked. New access requests go to each approver, decisions to the requester, and alerts to your team: failed rotations, JIT accounts that couldn't be removed, low disk, integrity and license problems, failover, and sessions ended by the keyword guard. Alerts of one kind within an hour arrive as one summary, and emails never contain passwords or recordings.
  • Recovery kit. For the day Vaultgate itself is unreachable: chosen emergency accounts in an encrypted file that opens in any browser offline, unlocked by a set number of recovery codes held by different people.
