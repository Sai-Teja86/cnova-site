Getting started

Architecture

Vaultgate is a single appliance that sits between your administrators and the systems they manage.

  • Vault: every password, key and secret is encrypted with AES-256-GCM, each with its own data key, wrapped by the appliance's master key. The database alone is useless without that key.
  • Session gateway: users open SSH, RDP and VNC sessions in the browser, or use their own SSH client through the SSH gateway. Vaultgate signs in with the vaulted credential, so users never see it, and records the session.
  • Rotation engine: changes passwords on servers, databases and network devices on a schedule, after use, or on demand, then signs in to confirm the new one works.
  • Policy engine: access is denied unless a policy grants it, to a user, role or directory group, for an account, asset or tag, optionally within time windows or after approval.
  • Audit trail: every sign-in, decision, reveal, session and change is written to an append-only, HMAC-chained log that shows any edit.

Requirements

  • Appliance: 2 vCPU, 4 GB memory, 40 GB disk or more (recordings need space). BIOS or UEFI; Secure Boot supported.
  • Witness (automatic failover only): 1 vCPU, 2 GB memory, 20 GB disk.
  • Platforms: VMware, Microsoft Hyper-V (Gen 1 and Gen 2), Proxmox, KVM, Nutanix AHV, or a physical x86-64 server.
  • Users: a current web browser. Nothing is installed on their computers.
  • Network: users reach the appliance on 443 (and 2200 for the SSH gateway). The appliance reaches your systems on their usual ports. See Ports and services.

Installation

Install the appliance

  1. Create a VM with the requirements above and attach the Vaultgate ISO. On Hyper-V Gen 2 with Secure Boot, choose the Microsoft UEFI Certificate Authority template.
  2. Boot it and choose Install. The installation is unattended and erases the first disk. It uses English, UTC and DHCP if available, and downloads nothing.
  3. The machine restarts into the appliance.

Every installation generates its own vault master key, TLS certificate, SSH gateway host key, appliance ID and database on first start. Nothing secret is shared between appliances or shipped on the ISO.

On Nutanix AHV with automatic failover, use a network without IP address management, or reserve the virtual address in it: AHV may drop traffic for addresses it didn't assign.

The server's console

The appliance's own screen shows the Vaultgate console menu. There is no login prompt and root is locked. From it you can:

  • read the web address and the one-time setup code (Status);
  • set the network (static address, gateway, DNS), host name and time servers;
  • replace the TLS certificate, restart services, read logs, reboot or shut down.

Setup wizard

  1. Open https://<appliance address>/. The browser warns about the self-signed certificate until you install your own.
  2. Enter the setup code from the server's console. It works once.
  3. Read and accept the license agreement, then create the first administrator. MFA is required by default: you set up an authenticator app next.
  4. You land on the License page: activate your license or continue on the 30-day trial.

The wizard also offers Restore from a backup, Set up as a standby and Set up as a witness. See Backup and Failover.

The two web consoles

  • https://<address>/: privileged access. Vault, policies, users, sessions, approvals, audit and reports.
  • https://<address>/appliance/: the appliance itself. License, Updates, Backup, Standby and failover, Storage and the Recovery Kit.

Both use the same administrator accounts, and a session started in one carries over to the other in the same browser tab.

TLS certificate

The appliance starts with a self-signed certificate. Replace it with one from your internal CA or a public CA from the server's console, so browsers, SSH-gateway users and the Credential API trust the appliance. Include every name and address users connect to, including the failover virtual address.

Licensing

Online activation

On the License page, enter your license key and click Activate. The appliance sends the key, its appliance ID, host name, version, installer build and the number of assets and users. No credentials, recordings or audit data leave the appliance.

It then checks in once a day and keeps working for 30 days without a check-in, so an internet outage doesn't stop it. Check in now retries straight away.

Offline activation

For appliances that can never reach the internet:

  1. On the License page, under Offline activation, enter the license key and click Make request code.
  2. Copy the code or save it as a file, and send it to Cnova from any computer.
  3. Upload the license file you receive, or paste its contents, and click Install license file.

An offline license never checks in: it works until the license expires, plus the grace period. When you renew, repeat these steps. A license file only works on the appliance that made the request.

License states

  • Trial: everything works for 30 days, up to 50 assets and 25 users.
  • Active: licensed. Warnings appear 30 days before expiry, or when a check-in is overdue.
  • Grace: the license has expired but still works for 14 days, with a warning.
  • Restricted: the trial or grace period ended, the license was revoked, check-ins stopped for too long, or the program files were changed.

When restricted, new sessions, check-outs, imports and new assets or users are refused. Administrators keep sign-in, the audit trail, reports, password retrieval, rotation, the Credential API and live sessions, so nobody is locked out of their own systems.

Updates and your license

Each license includes updates up to a date, normally the end of the license or support term (shown on the License page under Updates). An update released after that date is refused, with a message to renew. Updates released earlier still install.

Security-fix updates always install on a licensed appliance, whatever the dates, so a lapsed renewal never leaves a known hole open.

Configuration

Users, roles and MFA

  • Roles: admin (everything), approver (approves access requests), auditor (audit, reports, recordings, live monitoring), user (connects to what policies allow).
  • Passwords are hashed with Argon2id, at least 12 characters with upper- and lower-case letters and a digit. Repeated failures lock the account for a while.
  • MFA: time-based codes from any authenticator app. It can be required per user or for everyone. Keep at least two administrators with MFA, so one can always help the other.

Active Directory and LDAP

Go to Administration → Security Providers → Add Active Directory and enter the domain name, a domain controller, and an ordinary domain user with its password, used only to read the directory.

  1. Vaultgate connects over LDAPS (port 636) and shows the domain controller's certificate thumbprint. Confirm it.
  2. Groups: pick which directory groups give which role. Everyone else can't sign in, unless you choose a default role.
  3. Users: preview who will get which role, and import them before their first sign-in if you want.

Users then sign in as DOMAIN\user or user@domain. Their role is refreshed from their groups at every sign-in, and a sync (every 15 minutes by default) disables leavers and ends live sessions they're no longer allowed. Add as many domains and LDAP directories as you need.

Single sign-on

Add an OpenID Connect provider under Security Providers, and register https://<address>/api/auth/oidc/callback as the redirect address in your identity provider. Each provider gets its own sign-in button.

Link an SSO provider to the directory behind it, so its users get that directory's role mapping and leaver sync. MFA is then done by your identity provider.

Assets and accounts

An asset is a system: a Linux or Windows server, a database, a network device or a published application server. An account is a credential on it, stored in the vault. Tags on assets let one policy cover many systems.

A linked account is one credential used on many assets of the same protocol, such as a domain account on many Windows servers. Users choose the server when they connect.

Use Connection Test to check every asset's port and every account's sign-in in one click. Its Connect button opens a recorded test session as an administrator, without an access policy.

Bulk import and discovery

  • CSV import: assets and accounts with a full preview. Nothing is written while any row has an error.
  • Active Directory discovery: computers (added as RDP or SSH assets) and privileged or service accounts, chosen by group, OU, name or admin flag.
  • Windows local accounts: discovered over SMB on chosen servers.

With a control account, discovered accounts get a new password the moment they're vaulted, so you never need to know the current ones.

Control accounts

A control account is a privileged account Vaultgate uses to change other accounts' passwords: root or a sudo user on Linux, a local or domain administrator on Windows, a database administrator, or a device administrator. They have their own page, are off by default, and only administrators can retrieve them.

Rotation policies

A rotation policy sets how often a password changes, whether it changes after every use, its length and characters, and characters to avoid. Pick one per account, or None. After every change Vaultgate signs in with the new password to confirm it works.

  • Linux and Unix: the account changes its own password, or a control account changes it.
  • Windows: local and domain accounts.
  • Databases: SQL Server, Oracle, MySQL, MariaDB, PostgreSQL, MongoDB, Redis, Valkey, Cassandra and SAP HANA, each with its own statement. Db2 accounts are operating-system accounts.
  • Network devices: Cisco IOS and IOS-XE, and FortiGate, through a control account on the device.
  • Custom platforms: define your own command steps for systems not listed.

Device passwords can't contain spaces, quotes, ?, \ or !, and Oracle passwords can't contain a double quote. Exclude them in the policy; generated passwords avoid them automatically.

Access policies and approvals

Nobody can do anything until a policy allows it. A policy grants a user, role or directory group access to accounts, assets, tags or everything, and sets:

  • whether they may open sessions, reveal passwords, or both;
  • days and hours, and a maximum session length;
  • whether access needs approval (just-in-time): the user asks with a reason and duration, an approver accepts or refuses, and nobody approves their own request;
  • clipboard, file transfer, blocked commands, blocked words and the paste box.

Revoking access ends live sessions straight away; approved access expires on its own.

Personal JIT accounts

Instead of sharing a standing account, a policy can give each user their own account on the servers it covers. Tick Personal JIT accounts on the policy, scope it to an asset, a tag or all servers, and list the groups the account joins (for example sudo, or Remote Desktop Users).

  • The account is jit-<username>, so the server's own logs show who it was. It works for local, Active Directory, SSO and vendor users alike.
  • It's created at the user's first connection by the server's control account, with a random password that Vaultgate signs in with. Nobody ever sees it.
  • It's removed when the approved access ends or is revoked, or 10 minutes after the last session when the policy needs no approval. Live sessions end first; on Linux the user's processes are stopped and the home folder deleted.
  • Servers: Linux and Windows (local accounts). Each needs a control account: root or a sudo user on Linux, an administrator on Windows.
  • Active Directory: set the policy's Windows option to One domain account per user and give an OU. Each user then gets one domain account, created over LDAPS by a domain control account, that may sign in only to the servers the policy covers, joins the listed domain groups, and is deleted afterwards. The servers need DNS names, not IP addresses.
  • Databases: SQL Server, Oracle, MySQL, MariaDB and PostgreSQL get a personal login jit_<username> with the listed roles, made by the database's control account and dropped afterwards. On an application, choose each user's own personal JIT login on this database and every user who launches it gets their own login instead of a shared one.
  • Vaultgate never touches an account it didn't make. If a server is unreachable at removal time, it retries every 5 minutes; Vault → Personal JIT accounts → Check server lists any leftovers.

Check-out and check-in

When a policy allows reveals, a user can check a password out with a reason for a limited time. The account is locked to them while it's out. It's checked back in automatically when the time runs out, and its password can change on check-in, so a revealed password stops working.

RemoteApp applications

Programs published on a Windows RDS server, such as database tools or admin consoles, open as a single window in the browser, signed in with a vaulted account. A second vaulted credential can be passed to the program: as parameters of the published RemoteApp, or through a small launcher on the RDS server that runs as that account or types it into the login window.

Treat the RDS server as part of the vault's trust boundary: patch it and keep its local administrators few. Prefer runas /netonly or typing into the login window: parameters are visible to anyone who can list processes there.

Credential API

Scripts, scanners and pipelines fetch a password when they need it, so rotation never breaks them. Register each application under Credential API with the addresses it connects from and the accounts it may fetch. Its API key is shown once.

curl -H "Authorization: Bearer vgk_…" \
  "https://vaultgate.example.com/api/v1/credential?address=10.0.5.20&username=svc_scan&reason=weekly+scan"

Choose the account by address and username, by name=asset/username, or by account=<id>. Errors: 401 wrong key, 403 address or account not allowed, 404 no match, 409 more than one match, 429 rate limit. Ten failures in five minutes block the address for the rest of that window. Every fetch is audited.

File transfer and keyword guard

  • RDP file transfer: upload and download are separate switches, both off by default. Files go through a per-session drive that is wiped afterwards, and each file's name, size and SHA-256 are logged.
  • File checks: policies can block file types (by their real contents) and blocked words inside text, Office and zip files, in both directions.
  • Blocked words: in RDP, VNC and application sessions, typing a listed word warns the user or ends the session.
  • Paste box: with the clipboard off, users paste into a box that is checked before the text is typed into the session.

These are deterrents. Least-privilege accounts are the real control.

Daily use

Browser sessions

Users open My Access and click Connect. The session opens in its own browser tab: a terminal for SSH, a desktop for RDP and VNC, a single window for applications. Accounts that need approval show Request access instead. Idle sessions end after 15 minutes by default.

SSH gateway

Users who prefer their own tools connect on port 2200:

ssh -p 2200 alice@vaultgate                         # sign in, then choose a target
ssh -p 2200 alice+root@web-01@vaultgate             # straight to root on web-01
scp -P 2200 file.tgz alice+deploy@web-01@vaultgate:/tmp/
sftp -P 2200 alice+root@web-01@vaultgate

The part before + is the Vaultgate username, the part after it is account@asset. Directory users add their domain: ssh -p 2200 user@domain@vaultgate. Users sign in with their password or an SSH key added under My profile, then their MFA code. File transfer needs Allow file transfer on the policy. Port, agent and X11 forwarding are refused.

Publish the gateway's host-key fingerprint (shown on My profile) so users can check it the first time they connect.

Monitoring and replay

Under Sessions, auditors and administrators can watch a live session read-only, and administrators can end it. Sessions are recorded and sealed into the audit trail when they end. Replay checks the recording's integrity, then plays it with seeking. Commands and typed lines are indexed, so you can search across every recording and jump to the moment they were typed.

Recording choices and downloads

  • Not recording an asset: untick Record sessions on the asset (or put no in the record column of the CSV import), for example for test and UAT servers. Their sessions keep no screen recording or input log, so they use no recording space, but are still audited, command-indexed, filtered and watchable live.
  • Downloads are set on the Storage page: Encrypted (default), Plain or Off. Changing it needs your password and MFA code, and is audited.
  • Encrypted downloads: the console shows a passphrase when you download. The .vgrec file's key also needs a secret that never leaves the appliance, so it opens only on the appliance that made it (or its standby, or an appliance restored from its backup), under Sessions → Open recording file. It's decrypted in your browser. Each download and each opening is in the audit log. Keep the passphrase apart from the file, and keep backups: if the appliance and its backups are lost, its files can't be opened.
  • Plain downloads: an evidence package with the recording, a player that works in any browser, the session details and typed commands.
  • Retention is set on the Storage page. Recordings are kept forever until you set a period, and the shortest period is 180 days (CERT-In asks for 180 days of logs; 365 or more suits the DPDP Rules' one year). An appliance with a shorter period from before 0.1.0-48 is raised to 180 days, and that's audited. The audit log is never deleted.

Audit and reports

  • Audit Log: tabs for sign-ins, sessions, credentials, access, identity and configuration, in plain language, with CSV export. Verify integrity checks the whole chain.
  • Reports: a session report, an activity log and a PDF management report with usage, peak hours and findings such as failing rotations, stale passwords and administrators without MFA.

The chain detects edits, but not removal of the newest events. Turn on log forwarding so your SIEM holds an off-box copy as events happen.

Operations

Backup and restore

The Backup page (appliance console) creates an encrypted file with the database, vault master key, signing keys, TLS certificate and, optionally, recordings. You choose a passphrase. It isn't stored, so without it the file can't be opened.

To restore, install the same version or later on a new server and choose Restore from a backup in the setup wizard. Passwords rotated after the backup aren't in it. The license keeps working for 14 days: release the old appliance's seat, then activate the key again.

Recovery kit

For the day Vaultgate itself is down. The Recovery Kit seals chosen emergency accounts, such as a domain administrator, into one HTML file that opens in a browser with no network. Opening it needs a set number of recovery codes, for example any 2 of 3, each held by a different person.

  1. Choose only the accounts needed to get systems back. Automatic rotation stops for them.
  2. Create the codes and give each holder one. They're shown once.
  3. Download the kit, keep copies away from the appliance and the codes, and test-open it once with the network off.

The console warns when a password in the kit changes. Download a new kit; the codes stay the same.

Warm standby

  1. Install a second appliance, ideally on another host or site, and choose Set up as a standby in its wizard. It shows a pairing code once.
  2. On the primary, open Standby and enter the standby's address and code.

The primary sends an encrypted backup every 15 minutes by default, and within about a minute of any change. To fail over by hand, shut the primary down and promote the standby from its page with its setup code.

Automatic failover

Needs three appliances, ideally on three hosts: the primary, a paired standby and a small witness that decides which one may serve, so both never do.

  1. Install the witness and choose Set up as a witness. It shows a code once.
  2. On the primary's Standby page, under Automatic failover, enter the witness's address and code and a free virtual address, such as 192.168.110.130/24. Point users and DNS at the virtual address.

If the primary stops answering, the standby takes over the virtual address in about 45 seconds. Live sessions end; users reconnect to the same address. A replaced primary that comes back stops serving by itself.

Updates

Updates are signed bundles (.vgupdate) from Cnova. On the Updates page, upload the file. Vaultgate checks its signature, shows its notes, and installs it after your password and MFA code. It saves the current version and database first, and goes back automatically if the new version doesn't start properly.

  • With failover, install on the primary only: it updates the standby and witness first, then itself.
  • Operating system patches: appliances with internet access install Debian security updates by themselves. Offline appliances get them in update bundles, which install only packages newer than the appliance's own.
  • A new kernel takes effect at the next restart.

Email notifications

From 0.1.0-47, Vaultgate emails people through your own mail server or relay. Set it up in the appliance console → Notifications; saving asks for your password and authenticator code again.

  1. Mail server: its host name and port. Choose STARTTLS (usually 587) where you can, TLS (usually 465), or Not encrypted (25) only for an internal relay that needs no sign-in. The server's certificate is checked; for an internal mail server, paste the CA certificate that issued it.
  2. Sign-in: a name and password if your mail server needs them. The password is encrypted like vault secrets and never shown again.
  3. Sender address and the console address used for links in emails, such as https://pam.example.com.
  4. Alert recipients: one or more addresses, such as a security team mailbox.
  5. Tick the events you want, turn on Send email notifications, save, then Send a test message. The page shows exactly what your mail server answered.
  • To people: a new access request goes to each approver and administrator with an email address, one email each; the decision goes to the requester. Addresses come from the user's profile or the directory's mail attribute.
  • Alerts: failed or paused password rotations, personal JIT accounts that couldn't be removed, low disk space, failed program file checks or a broken audit chain, license warnings (when the state changes, then weekly), failover and standby sync problems, and sessions ended by the keyword guard.
  • Grouping: the first alert of a kind is sent at once; more of the same kind within an hour arrive as one summary.
  • Delivery: emails are sent in the background and retried for a day, waiting longer each time. The Outbox lists each email with its status and the mail server's last answer, and Send now retries one. While email isn't getting through, the PAM console shows a warning.

Emails never contain passwords, keys, recordings or command output: they say what happened and link to the console. Approving or denying a request always needs a sign-in. Every email sent or failed is in the audit log.

Log forwarding to a SIEM

From 0.1.0-48, Vaultgate sends every audit event, as it's written, to your syslog collector or SIEM. Set it up in the appliance console → Log forwarding; saving asks for your password and authenticator code again.

  1. Collector: host name or address and port. Choose TLS (usually 6514) where you can; TCP or UDP (514) send in the clear. For TLS the collector's certificate is checked: for an internal CA, paste its certificate.
  2. Framing (TCP and TLS): octet counting (RFC 6587, the standard for syslog over TLS) or one message per line, whichever your collector expects.
  3. Facility: authpriv by default, or log audit, local0 to local7.
  4. When you first turn it on, choose new events only, or the whole audit log first to give your SIEM the history too. Then Send a test message and look for action siem.test.

Each message is RFC 5424 syslog: app name vaultgate, the action as the message ID (such as auth.login), severity informational for successes and warning for failures. The body is JSON:

{"id": 4182, "time": "2026-12-01T09:14:03.512000Z", "appliance": "pam01", "action": "credential.reveal",
 "label": "Password revealed", "summary": "…", "actor": "asha", "target": "account:12", "outcome": "success",
 "ip": "10.1.4.20", "detail": {…}, "hash": "…", "prev_hash": "…"}
  • Nothing lost: Vaultgate remembers the last event the collector took. While it's unreachable, events wait on the appliance and are sent oldest first once it's back. Over TCP and TLS a batch counts as sent only after the collector has read it. UDP can lose messages unnoticed.
  • Checking the copy: hash and prev_hash link each event to the one before. A gap in id or a broken link in your SIEM shows an event is missing; the appliance's Verify integrity checks the source.
  • Alerts: if the collector stays unreachable for 5 minutes, an audit event and an email alert say so, and both consoles show a warning until it's back.

Time and NTP

Audit timestamps and recordings are evidence, so the appliance's clock must be right. In India, CERT-In's directions ask that clocks be synchronised to the NTP servers of NIC or NPL, or to your own NTP servers synchronised to them.

  • The appliance console → Time page shows whether the clock is synchronised, its offset and each NTP server's state.
  • Enter up to 8 servers and save; Use NIC and NPL servers fills in samay1.nic.in, samay2.nic.in and time.nplindia.org. Check CERT-In's current list, and that the appliance can reach UDP port 123. Empty means Debian's public pool.
  • The server's text console (Time zone and NTP) sets the same servers, and the time zone. Audit times are stored in UTC and shown in your browser's time.
  • If the clock loses sync, or drifts more than a second, an audit event and an email alert say so, and the consoles show a warning.
  • No time server reachable, as on an isolated network? While the clock isn't synchronised, the Time page offers Set the clock from this computer: it shows this computer's time beside the appliance's, and sets the appliance to it, to within about a second. It asks for your password again and is recorded in the audit log. A time server, once one answers, takes over again.

Network tools

When a session, password rotation or test login fails, first check that the appliance can reach the server. The appliance console → Network tools page runs the checks from the appliance itself, which can see a different network from your own computer.

  • Ping: ICMP echo, 1 to 10 packets. No reply doesn't always mean the server is down: many servers and firewalls drop ping.
  • Traceroute: the routers on the way, over ICMP or UDP. A * row is a router that doesn't answer, which is common; it matters only if the trace stops there.
  • Port check: opens a TCP connection to the port Vaultgate uses for the asset and shows what the service says first (an SSH server's version, for example). "Refused" means the server answered but nothing listens on that port; "no answer" usually means a firewall drops it.
  • DNS lookup: resolves a name with the appliance's DNS servers, or finds the name of an address.

Pick an asset to fill in its address and port. Only administrators can run checks, at most three at a time, and each one is recorded in the audit log.

Troubleshooting

The web console is unreachable

  • Check the address on the server console's Status page, and that you use https://.
  • Check that port 443 is allowed from your network to the appliance.
  • With failover, use the virtual address. If the primary was replaced, its console says it stopped serving.
  • Restart the services from the server's console, and read its logs.

A session won't connect

  • Run Connection Test on the account: it separates a closed port from a wrong password.
  • Host key changed: Vaultgate refuses to connect when an SSH server's key changes, in case of interception. If the server was rebuilt, an administrator resets the pinned key on the asset.
  • RDP certificate: certificates are checked by default. Give the server a certificate trusted by your CA. Accept untrusted certificates is for labs only.
  • Not allowed: check the policy's days and hours, whether approval is needed, and whether the license is restricted.

Rotation failed

  • Check the control account still works (Connection Test), and that it has the rights to change that account.
  • Check the rotation policy's characters against the platform's limits. See Rotation policies.
  • The failure, with the system's error, is in the Audit Log and on the PDF report's findings.

Directory sign-in fails

  • Test on the security provider checks the connection and looks one user up.
  • Port 636 must be open to a domain controller, and its certificate must match the thumbprint you confirmed.
  • Users in no mapped group are refused by design. Check their groups on the provider's Users tab.
  • A directory user can't take over a local account with the same name; that attempt is refused and audited.

License problems

  • Can't reach the licensing server: allow outbound 443 to it, or use offline activation. The appliance keeps working for 30 days meanwhile.
  • Issued for another appliance: the license is tied to one appliance. After cloning or rebuilding a VM, activate again, and ask Cnova to release the old seat if needed.
  • Program files have been changed: the appliance found its files differ from the signed list made at build time. Reinstall from an official installer or apply an official update. The audit log names the files.

An update was refused

  • Signature not valid: the file was damaged or didn't come from Cnova. Download it again.
  • Not newer: that version, or a newer one, is already installed.
  • Updates ended: the update was released after your license's update date. Renew, or apply the latest security-fix update.
  • Rolled back: the new version didn't start properly, so the previous one was restored. Send the result from the Updates page to support.

Failover is paused

A banner appears when the witness or the standby can't be reached. Service continues, but automatic failover can't happen until both are back. If the primary restarts while the witness is down, it waits for the witness before taking the virtual address; an administrator can override this on the Standby page.

SSH client warnings

  • Unknown host key on first connect: compare it with the fingerprint on My profile.
  • OpenSSH 10 post-quantum warning: the gateway doesn't offer a post-quantum key exchange yet. The connection is still encrypted with a standard key exchange.

Emails don't arrive

  • On the Notifications page, check that email is On and the event is ticked. People need an email address on their user.
  • Use Send a test message and read the answer: sign-in refused (535) means a wrong name or password; isn't trusted means the mail server's CA certificate is missing; doesn't offer STARTTLS means use TLS on 465, or an internal relay on 25; can't reach means a network or firewall problem between the appliance and the mail server.
  • The Outbox shows each email's last error. After fixing the settings, Send now retries it.
  • The test arrives but alerts don't: check the alert recipients, and your spam filter. Many alerts of one kind arrive as one summary an hour later.

Events don't reach the SIEM

  • Use Send a test message on the Log forwarding page: can't reach means a network or firewall problem, or nothing listening on that port; isn't trusted means the collector's CA certificate is missing.
  • The test arrives but events look garbled or run together: switch framing. Collectors that expect one message per line show octet-counted messages with a number in front.
  • Events waiting on the page counts what the collector hasn't had yet. They're sent in order once it's reachable; nothing needs re-sending by hand.
