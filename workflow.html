How Vaultgate works, step by step

The everyday journeys for users, approvers, administrators and applications.

1. Opening a session

An engineer needs to work on a server. They never see its password.

  1. Sign inWith their directory account or single sign-on, plus a second factor.
  2. Pick a targetMy Access lists only what policies allow them, right now.
  3. Policy checkVaultgate checks the user, the time window and any approval again at connect time.
  4. Gateway signs inThe password comes from the vault and goes straight to the server, not to the browser.
  5. Work, recordedCommands are checked against the blocklist; everything is recorded.
  6. Session endsThe recording is sealed into the audit trail. The password can rotate now.

2. Requesting access just in time

For sensitive systems, nobody has standing access. They ask, someone approves, and it ends on its own.

  1. RequestThe user asks for a target, with a reason and how long they need.
  2. ApproveAn approver sees the request and approves or refuses it. Nobody approves their own.
  3. UseThe user connects as usual, within the approved time.
  4. ExpireAccess ends at the set time. Revoking it early ends any live session.

3. Password rotation

Every password changes on schedule, and Vaultgate proves the new one works.

  1. TriggerThe rotation policy's schedule, the end of a session, a check-in, or an administrator.
  2. GenerateA new password that follows the policy's length and character rules.
  3. ChangeUsing the system's own command, by the account itself or through a control account.
  4. VerifyVaultgate signs in with the new password.
  5. StoreThe new version is saved and the change is written to the audit trail.

4. Checking out a password

When someone really needs to type a password themselves, for example on a console with no network.

  1. Check outWith a reason. The account is locked to that person.
  2. UseThe password is shown once and the reveal is audited.
  3. Check inBy the user, or automatically when time runs out.
  4. RotateOptionally, the password changes on check-in, so the copy they saw is useless.

5. Onboarding servers and accounts

How an administrator brings systems under management.

  1. Add serversOne by one, from a CSV file, or found in Active Directory.
  2. Add accountsTyped in, imported, or discovered by group, OU or on the server itself.
  3. Set a control accountAn administrator login on the server, kept for rotation only.
  4. Rotate on importEach account gets a fresh password, so nobody needs the current one.
  5. TestThe connection test checks every port and sign-in in one click.
  6. GrantWrite policies for who may use what, and when.

6. Applications fetching passwords

Scanners, CI pipelines and scripts get the current password when they run, instead of keeping their own copy.

  1. RegisterThe administrator creates an API client with its key, allowed addresses and accounts.
  2. RequestThe application calls the Credential API over HTTPS with its key.
  3. CheckKey, source address, allowed account, rate limit and reason are all checked.
  4. DeliverThe current password is returned and the fetch is audited.

7. Review and audit

What auditors and security teams do with the evidence.

  1. Watch liveJoin any running session read-only, and end it if needed.
  2. SearchFind a command or typed line across all recordings.
  3. ReplayOpen the recording; its integrity is checked against the sealed hash.
  4. Verify the logCheck the audit trail's chain for tampering in one click.
  5. ReportExport CSV, or produce the PDF management report.
